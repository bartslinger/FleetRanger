# Architecture decisions

The decisions made so far, each with a short reason. Open questions are listed in [roadmap.md](roadmap.md).

## Deployment

- **One install per organisation.** Flight data is sensitive, so each organisation runs its own server. Several installs may share one DJI app key.
- **Docker Compose** with three containers: `backend` (Rust), `web` (SvelteKit), `postgres`. TLS and certificates are handled by nginx on the host, which proxies to containers bound to `127.0.0.1`.
- **Images are built on a developer machine** and loaded onto the server. Servers can be small, and compiling Rust on them is impractical. Images target x86_64 and are cross-compiled rather than emulated.
- **Images ship without a registry.** `deploy/ship-image.sh` builds the backend and web images and loads them on the server over SSH.
- **Releases are tags** (user's decision, 2026-10-19): only a commit tagged `vX.Y.Z` is a server release, and both images carry that tag; `ship-image.sh` refuses an untagged commit or a dirty tree. The Android app has its own `android-vX.Y.Z` tags. nginx sends `/api/` and `/auth/` to the backend and everything else to the web app.
- **First release on the first organisation's server** (user's decision, 2026-10-19), without backups at first (user's choice: the raw logs also exist on the controllers and the earlier sync).
- **Internal secrets are generated on the server** (database password, signing keys) and never leave it. External secrets (DJI app key, OIDC client secret) are kept in an Ansible vault.
- **Remote controllers sync over the internet** to the install's public HTTPS endpoint.

## Data

- **PostgreSQL**, without PostGIS for now. Flight tracks are stored as GeoJSON LineStrings in a `jsonb` column on `flights`. Postgres keeps large values out of line, so listings that don't select the track stay light. Moving to PostGIS later is a single backfill with `ST_GeomFromGeoJSON`.
- **Raw logs are files on disk**, stored as `raw/<controller serial>/FlightRecord/<file name>`: the file name as it was on the controller, under the serial of the controller that sent it, as logs synced before FleetRanger already were. The path says where a log came from, so the database records only its hash, path and the pilot chosen on the controller; identical files are stored once. A log is never modified, except that an upload to an existing path with different content (an unfinished log, uploaded again once DJI Pilot 2 finished writing it) replaces it and is processed again, updating its flight in place.
- **Raw logs and flights are separate tables.** A raw log is a file and its processing state; a flight is what was derived from it. A log without a takeoff has no flight, and a log is assumed to hold at most one flight until one turns up with several. Re-processing updates a flight in place, so what is attached to it (pilot, session) survives.
- **Flight tracks are kept at one point per second.** More detail can be derived from the raw log when needed.
- **Columns only for what features use**: shown in lists, sorted, filtered, summed or needed by access rules. Display-only summaries go in a `metrics` jsonb column, typed in code, and are promoted to a column when a feature needs one. `metrics` never holds time series. Everything else stays in the raw log until a feature needs it, then logs are re-processed.
- **Statistics are computed by FleetRanger from the frames**, not taken from the summary DJI's app writes into the log, so they match the track and the method is known. "In the air" is the flight controller's on-ground flag: a log with no frame in the air is not a flight, and air time runs from lifting off to touching down. DJI records logs only while the motors run, and its timer counts motor time, which is typically 2–3 seconds longer per flight.
- **Raw logs and full telemetry are not exposed** to any user, admins included. They exist so logs can be re-processed when the parser improves. Users only see derived data (times, distance, track, statistics).
- **Every DJI keychain request is recorded** per log: the exact request sent (API key redacted), the time, the response status and the keys returned.
- **A keychain request carries no flight data** (checked 2026-10-20). The body holds the log format version, the number of the DJI app that wrote the log, and per feature point its fixed name and the encrypted key block from the log's KeyStorage record. The headers add the API key, the content type and the HTTP client's standard headers. All 244 requests stored on dev were 4,244 bytes, and every byte is accounted for: ten 256-byte key blocks in base64 (3,440), the names (365) and the JSON around them. The key blocks are RSA-2048 with PKCS#1 v1.5 padding, so only DJI can open them. In the code of DJI Pilot 2 17.3.0.21 (its flight record library, read from the APK on the test controller), each one holds only a 32-byte AES key and a 16-byte IV that the app generates when it writes the log: no serial numbers, positions, times or other log data. DJI does see the API key, the server's address and when each request is made, and with the keys it could read a log it got hold of; FleetRanger never sends one. Recheck after major DJI Pilot 2 updates.

## Identity and access

- **Login via OpenID Connect**, with Google first. Sessions are stored on the server, so they can be revoked immediately and audit records reference them.
- **The backend runs the login**: authorization code flow with PKCE, the provider found through its issuer URL. One provider per install for now.
- **Everyone is a user.** Pilots, viewers and admins are all users, with one name entered by an admin. A user has roles (see "Groups and roles"), can log in, or both. Only admins create users, also for pilots; the remote controller only downloads the list (see "Clients"). That avoids duplicates, so there is no merging of users.
- **Logins are separate from users.** A user can have a login: an email address, tied to the provider's subject ID on first use. Login data (`logins`, `login_sessions`) is kept apart from what a user is, so the security-sensitive part stays small. Removing a login stops someone from logging in while they keep flying.
- **No open sign-up.** An admin gives a user a login by email. The first login with that verified email ties it to the provider's permanent subject ID, and later logins match on that ID only, so a reassigned or renamed address can't take over or lock out a login. The first user of an install is added with `fleetranger add-user --admin <email> <name>`.
- **Apps act for a user through OAuth** (user's decisions, 2026-10-20), FleetRanger being the authorization server: first AI assistants over MCP, later other integrations, so it is a module of its own (`oauth`) and not part of MCP. Apps register themselves (dynamic client registration), which grants nothing; a logged-in user allows one on the consent page (`/connect`), which says what the app will and won't be able to do; the app exchanges the code (PKCE) for an access token (an hour) and a refresh token (replaced at every use, ending after 30 days without use). Every token carries its scopes (only `flights:read` so far) and the resource it is for (e.g. `/mcp`), so a token for one part doesn't work for another; what a resource then allows is its own rule. Users see and disconnect their connected apps in the web app; archiving a user or removing their login disconnects them too. Codes and tokens are stored only as SHA-256 hashes. Apps acting without a user (client credentials, e.g. another system's backend) wait until a real integration needs them. A refresh token that comes back after it was replaced was copied, so the connection ends for both holders (refresh token reuse detection; user's decision after the security review, 2026-10-20). How (my choices, several after that review): only apps without a secret, as assistants are; return addresses must be HTTPS or on the user's own computer, where any port is allowed (RFC 8252); a registration is at most 8 KB, and apps never connected are removed a day after registering, by an hourly clean-up; the consent page and Connected apps show the app's return host apart from its name, since the name is only what it says it is; the consent page refuses a request naming a form action, and its buttons carry only the checked request; no page may be framed by another site. A rate limit on registration belongs in nginx.
- **Login sessions** (named so to tell them apart from flight sessions) are a random token in the cookie; the database stores only its SHA-256 hash. They expire after 30 days without use. Archiving a user or removing their login revokes their sessions.
- **Impersonation** (user's decisions, 2026-10-24; first called "View as", renamed as it does more than view): an admin (`users.manage` on the organisation) can impersonate any other user who isn't archived, with or without a login, to see what they see and for support. Changes are allowed and made as that user. Every page shows it in a banner at the top, with Stop impersonating; logging out ends it too. How (my choices): a cookie holds the impersonated user, so no schema change; it counts only next to the admin's own login session and while that login may manage users, otherwise it is ignored, and requests then act as that user with their roles (the `Actor` also carries the admin). MCP and the controller app don't send it. The audit log will record both.
- **Impersonation in apps** (user's decision, 2026-10-25): an admin who impersonates someone and opens an app connects it as that person, to see the app as they do. The connection records the admin, ends with the impersonation (Stop impersonating, switching to someone else, logging out), and isn't in that person's connected apps. Apps aren't told about the impersonation for now (user's decision, 2026-10-25): `impersonated_by` in `/api/v1/me` can be added when an app needs it. FleetRanger can't log anyone out of an app: it takes back the app's tokens, so apps check the login with FleetRanger on every page load and switch back on the next one (acceptable for an admin-only feature, user, 2026-10-25). Back-channel logout, where FleetRanger tells the app at once, can follow later.
- **Archived, not deleted.** Users that are no longer active are archived, so flights and history keep referring to them. An archived user can't log in and can't be chosen as a pilot. A user without flights can be deleted, for example one created by mistake.
- **Drones and remote controllers** belong to the organisation, in a group or directly in it (see "Groups and roles"). They are registered automatically from the serials in imported logs; flights keep the serials as text.
- **One table per kind of equipment** (`aircraft`, `remote_controllers`, `batteries`), not one devices table: they share a few columns but will differ, for example controllers get enrollment and sync settings.
- **Who sees a flight:** its pilot, and whoever holds `flights.read` on its group or on the organisation (see "Groups and roles"); later, people it has been shared with.
- **Archiving flights** (user's decisions, 2026-10-20): a flight that should count as not having happened is archived, never deleted (`flights.archived_at`). Only a flight without a session can be archived (user's decision, 2026-10-23): taking it out of its session first needs `sessions.edit` on that session, so archiving never changes another group's session. An archived flight is left out everywhere: lists, sessions, suggestions, totals, filter options and the equipment's last flight. Flights shows them with an "Archived" filter, with an "Archived" tag and Restore; a restored flight comes back without a session. Archived flights can't be added to a session, and an upload of the same log again leaves its flight archived. Archiving and restoring need `flights.archive` on the flights' groups (see "Groups and roles"). Who archived a flight is for the audit log, not a column.
- **Equipment pages:** who sees and changes a drone or controller is under "Equipment" in "Groups and roles". A flight's page links its drone and controller to their pages, and each page links to its flights in the logbook, which filters by drone and controller.
- **All access decisions go through one policy module** in the backend, never through ad-hoc checks in handlers. Service functions take an `Actor` (who is acting), so a handler can't skip the check.
- **Simplicity first.** The visibility condition is written directly in the flight queries, with a test that list and single-flight access agree. It gets extracted (for example into a SQL function) only when duplication becomes a problem.
- **Audit log:** append-only, recording every view, change, reassignment, move and merge, with the user, session, time and IP. There is no hash chain.

## Groups and roles

User's decisions, 2026-10-23, unless marked as mine. They replaced teams, the three fixed roles (member, all flights, admin) and holders. Groups come before serving several organisations from one install.

**The model**

- **Scoped roles**, as most large vendors have them (Google Cloud, Azure, GitHub): who may do what, on which part of the organisation. Permissions are fixed in code as small verbs, such as `flights.read`; the code never asks whether someone is an admin, so organisations with other structures fit without new code.
- **Roles are named sets of permissions, and building blocks:** Viewer, Pilot and Editor, combined per person, so no combined roles are needed. Each role includes the permissions it depends on (Editor includes Viewer's), so any single role makes sense on its own. A person's rights on a resource are the union of the roles of their membership of its group and their roles on the whole organisation; nothing denies. Roles an organisation defines itself can come later.
- **Access hangs on the resource's group, not on its pilot.** Rejected: permissions from person to person ("A reads B's flights"), which leaves flights without a pilot, equipment and sessions without an owner, can't keep a pilot's flights for two groups apart, and multiplies grants. Sharing with people can come later, beside the roles.
- **Admin work is organisation-wide only, for now.** Groups get Viewer, Pilot and Editor; Admin is a role on the whole organisation, and only admins give roles. Group-level admins must stay easy to add (user's requirement): admin work is checked as a permission on every group involved, both groups for a move, so a Manager role later only grants those permissions on a group, plus two checks (nobody grants roles they don't hold, a group keeps a Manager) (my design).
- **The last active admin can't lose Admin or be archived**, so nobody locks the organisation out through the app.
- **With another active admin, an admin may give up their own Admin** (user's decision, 2026-10-23), replacing "admins can't change their own role"; they still can't archive or delete themselves or remove their own login.
- How (my choices): the server checks the last admin with the active admins locked, and the Edit roles dialogs disable the last admin's Admin checkbox, saying why beside it (only admins see these pages, so the last admin only meets it on their own roles, where Archive isn't offered anyway). Giving roles in a group, renaming and deleting it need `groups.manage` on that group, creating one on the organisation.

**Groups**

- **A group has members and holds flights, sessions, drones and controllers**, each of which is in at most one group or directly in the organisation. A small organisation needs no groups: everything sits in the organisation, with roles on the whole organisation, and no group is ever chosen.
- **A membership means belonging to the group** and carries the person's roles there: one list per group, with pilots, overseers and viewers, answers both who is in it and what they may do. A person can be in any number of groups. Rejected: assignments apart from memberships, such as "the members of one group get a role on another", for which no case was found.
- **Adding a member preselects no roles:** the admin chooses at least one, and the group's page shows which members fly.
- **Roles in groups are managed from both sides** (user's decision, 2026-10-23): a group's page adds members and edits their roles, and a user's page adds them to groups and edits their roles there, the same way: a dialog per change that applies at once, apart from the page's form.
- **Groups aren't archived, for now.** Only an empty group can be deleted; otherwise "Delete group" first moves its flights, sessions and equipment to another group or the organisation in one step, which needs `groups.manage` and the move permissions on both sides. Its memberships go with it. Archiving can come if reports per group over past years need it.
- **Nested groups come later:** a role on a group will cover its subgroups. To begin with, groups are a flat list.
- **The UI shows the organisation as the top group** (user's decisions, 2026-10-23), with the same patterns as a group; the schema stays as it is (`organisation_roles`, null `group_id`):
  - **Its members are all users:** the Users list is the organisation's member list, its roles column the roles on the organisation; "New user" adds a member. The navigation keeps "Users" and "Groups"; the Groups list starts with the organisation ("Organisation, all users"), linking to Users.
  - **A user's page lists the organisation as the first of their groups**, its roles edited as a group's are; the form keeps name and email. The last admin keeps Admin there.
  - **What has no group is in "Organisation"**, one word everywhere: pickers ("Move to group", a session's group) start with it, a flight's group shows it, and the group filter offers it. "Queue" goes from the UI; uploads that still need a group are that filter.

**Permissions**, built-in roles (my proposal from the decisions):

| Permission | Viewer | Pilot | Editor | Admin |
|---|---|---|---|---|
| `flights.read`, `equipment.read` | ✓ | | ✓ | ✓ |
| `flights.fly_for` | | ✓ | | |
| `controllers.pair` | | ✓ | ✓ | ✓ |
| `flights.set_pilot`, `flights.archive`, `sessions.edit`, `equipment.rename` | | | ✓ | ✓ |
| `flights.move`, `sessions.move`, `equipment.move`, `batteries.rename` | | | | ✓ |
| `controllers.manage` | | | | ✓ |
| `users.manage`, `groups.manage`, `areas.manage`, `logs.manage`, `apps.manage` | | | | ✓ |

- **Two permissions for admin work the table first lacked** (user's decision, 2026-10-23, my proposal): `controllers.manage` on a group, for unpairing its controllers and seeing and revoking others' pairing codes for it; `logs.manage` on the organisation, for log processing.
- **`apps.manage`** on the organisation, for adding trusted apps (my choice, 2026-10-25): given to Admin like the other admin pages.

- **Admin doesn't include `flights.fly_for`** (user's decision, 2026-10-23): it puts someone in pilot lists, so an admin who flies also gets Pilot, in a group or on the whole organisation.
- **Pilot doesn't read the group's flights:** a pilot always sees their own, so a guest pilot sees only theirs. A pilot who should see the group's work also gets Viewer or Editor.
- **Pilot can pair controllers**, so pilots set up controllers in the field without waiting for an editor.
- Batteries and areas have no group, so their permissions count only on the whole organisation. `equipment.*` covers drones and controllers together while their rules are the same.

**Flights and pilots**

- **A flight's pilot and its group are independent:** the group is who the flight was for, the pilot who flew it. Setting a pilot never moves the flight, moving a flight never changes its pilot, and a pilot who leaves a group leaves nothing inconsistent. The pilot always sees their own flights, also after leaving, but not the rest of a session their flight is in.
- **Flying comes only from `flights.fly_for`.** Pilot lists, on the controller and in the web app, hold the people with it anywhere, so viewers and admins who don't fly never appear. The web app puts the flight's group's own pilots (its members with Pilot) on top, offers all pilots for flights in the queue, and the server checks the same when a pilot is set; flights keep their pilot when someone later loses the role.
- **On the controller the group is chosen after the pilot**, and only when the organisation has groups: it offers the groups the pilot is a member of and flies for, and has "Other group" for the other groups where they hold `flights.fly_for`. It picks the group itself only when the pilot may fly for just one; a single group of their own beside others still gets the choice, so the others can be reached. The choice has no "no group" (user's decisions, 2026-10-23). It is a screen of its own after the pilot's, built the same way (user's decision, 2026-10-23): "Log flights under" with the last group as the tile that opens DJI Pilot 2, and "Other group" for a list of their own groups and then the other ones; the pilot's tile leads there instead of opening DJI Pilot 2. The same pilot and group again are two taps then, and changing only the group doesn't go through "Other pilot". The wording is the user's: the choice counts until someone changes it, and user-facing text doesn't stress the word "group". An organisation where every pilot may fly for every group gives Pilot on the whole organisation. As pilots don't log in on the controller, this guides the choice rather than enforcing it.
- **A flight without a chosen group goes to the organisation's queue:** "Not in the list", a pilot without `flights.fly_for` and imported logs, including a first upload of years of logs. Only a choice gives a flight its group; the controller's and drone's groups play no part. Hints that uploads wait in the queue can come later.
- **Moving flights between groups is admin work.**
- **Changes to flights work on many at once** (batch actions in the logbook), and need the permission on every flight's group. A batch is applied whole or not at all.
- How (my choices): an upload keeps its pilot when they are active and hold `flights.fly_for` somewhere, as a pilot set by hand must; the controller's choice of group is checked when the log is processed. The pilot list (`/api/flights/choices`) gives the groups each pilot flies for as a member; a pilot field for flights of one group lists that group's pilots first under "North pilots", then "Other pilots" (native option groups, the carbon-expert's suggestion; Carbon is silent on them), and one list otherwise.

**Sessions**

- **A session has a group as its owner**, which decides who edits it and will own its report data. Sessions sit beside the tree, a way to organise and report on flights: their flights keep their own groups, so a session can mix groups, and a session of one group with another group's flights is accepted.
- **A flight is in at most one session**, so totals over sessions count each flight once and "without session" means still to be organised. Overlapping views, such as a joint mission seen by both groups, can come later as a concept of their own.
- **Changing which session a flight is in needs `sessions.edit` on every session that changes**, the one it joins and the one it leaves, so nobody changes another group's session. The flight's own group isn't checked: a session never changes it.
- **A session's group:** the flight's group when an upload starts one; made by hand, the creator chooses among the groups where they hold `sessions.edit`, with the flights' group preselected and no choice when there is one (until people find it confusing). A session can have no group, at organisation level.
- **Changing a session's group is admin work**, and asks whether to move its flights to that group as well.
- **Uploads are grouped per pilot and group:** an uploaded flight joins only a session of its own group, and a session it starts gets that group.
- **The Sessions list shows each session's own group, and its group filter goes by it** (user's decision, 2026-10-23): "North's sessions" are those North owns; the other filters still go by a session's flights.
- How (my choices): only flights the person sees go into a session. The web app offers the groups where the person holds `sessions.edit`, and the whole organisation when they hold it there; on a suggested session the field takes the Group fact's place, so creating stays one click (carbon-expert's advice). Made by hand without a group given (the API allows it), a session gets the flights' group when they share one, else the organisation. A split keeps the session's group, and merging keeps the group of the session that remains. `sessions.edit` is checked on the sessions flights join and leave, not on the flights' groups.

**Equipment**

- **Pairing gives the controller a group:** whoever creates the code chooses one of the groups where they hold `controllers.pair`, chosen already when there is one. Holding it on the organisation offers every group and the organisation itself, for a controller shared by several groups (user's decision, 2026-10-23). Without `controllers.pair` anywhere, nobody creates codes.
- **Equipment is also seen by whoever sees one of its flights**, as batteries are, so a drone shared by several groups simply sits in the organisation. Seeing a device means its row in Equipment, its page and the link from a flight; its flights stay those the user sees anyway.
- **A device's figures count all its flights:** total air time, number of flights, a battery's capacity and cycles, and the battery's health chart with a point per flight. They describe the machine's wear; points of flights the user can't see link to nothing, and each flight's own details (such as charge at takeoff and landing) stay with the flights the user sees.
- **Holders are dropped:** a device shows who flew it last, from its last flight, instead of a hand-kept field that goes stale.
- **Who flew it last comes from its last flight overall, but the name only shows to whoever may see that flight** (user's decision, 2026-10-23): others see that someone flew it then, without the name, so the answer is never an older, wrong pilot and never reveals who flew a flight the user can't see.
- How (my choices): renaming needs `equipment.rename` only when the name changes, and moving `equipment.move` only when the group changes. A drone or controller seen only through an archived flight isn't seen, as archived flights are left out everywhere; its link on that flight's page then finds nothing.

**Elsewhere**

- **The word "team" is gone** (user's decision, 2026-10-23): from the API, the code, the web app, the controller app and the docs. Only the unversioned endpoints kept for android-v0.3.0 still say "team" (see "Clients").
- **Archiving flights stays** a soft delete, with `flights.archive`, for flights without a session. A flight in a session is first removed from it, as a step of its own (user's decision, 2026-10-23, dropping "Remove from session and archive" in one step). How (my choices): a flight's page shows Archive only for a flight without a session; Flights refuses a batch with a flight in a session, with the reason.
- **Migrating changes nobody's access:** teams become groups, every team member becomes a member with Pilot and Editor, admins get Admin and the all-flights role Viewer on the whole organisation. Pilot lists are tidied by hand afterwards. Operations, never built, are dropped: merged sessions cover joint missions.

**Storage** (schema approved by the user, 2026-10-23; the shape is my proposal)

- **`groups`, `group_members` and `organisation_roles`**, with a nullable `group_id` on flights, sessions, drones and controllers: null is directly in the organisation (for flights, the queue). A group with anything in it can't be deleted.
- **A membership is one row per role** (`group_id`, `user_id`, `role`), so a membership always has a role and a check is a plain `role in (…)`. Roles are text with a check constraint (Viewer, Pilot, Editor in groups; also Admin on the organisation) until organisations define their own.
- **Checks read only the groups tables, with no dual write** (user's decision, 2026-10-23).
- **Teams, `team_members`, `users.role`, holders and the `team_id` columns of flights, drones and controllers were dropped** (migration 0020) once the code read and wrote only the groups tables (user's decision, 2026-10-23, package 6). The two other team columns, on `raw_logs` (the group chosen on the controller) and `pairing_codes` (the group a controller joins), became `group_id` (migration 0019). A deleted group leaves its raw logs without one, as their flights have moved on, and takes its open pairing codes with it rather than pairing into the organisation (my choices).
- **The check in code** (my design): each request reads the actor's roles once (`policy::Grants`); `may(permission, group)` counts the roles on that group and on the organisation, and the list filter is the groups where they hold a permission, or all of them. Batches need the permission on every group involved. `/api/me` gives the permissions held on the organisation and, per group, what the memberships add; the web app checks them by the same rule (`web/src/lib/permissions.ts`) to offer only what is allowed, and the backend still checks every request.
- **Teams became groups with the same ids** (migration 0018), so the remaining team columns (`raw_logs`, `pairing_codes`) moved over without a lookup. A session got its flights' group when they all had one team; a session of mixed teams or with queue flights went to the organisation (none existed). Archived teams would have become ordinary groups (none existed).

## Sessions

- **Sessions exist for reporting:** they summarise several flights as one thing.
- **A session is one pilot's consecutive flights**, for example a morning shift. A remote controller often powers off during a session while the pilot relocates, and the pilot may drive several kilometres between flights, so neither power cycles nor distance are boundaries.
- **Flights join sessions by themselves only when they are uploaded** (user's decision, 2026-10-19): sessions should never change unexpectedly, and the rest goes through people (and later suggestions they review). A flight uploaded with its pilot joins the pilot's session of the flight's group (see "Groups and roles"; a pilot may fly for two groups in one evening) when it is less than the gap away from one of its flights (2 hours, `FLEETRANGER_SESSION_GAP_MINUTES`) and that session's flights came in less than 12 hours before it, the same night's sync; with no such session it starts a new one. A later flight stays without a session, for someone to add. This happens only the first time a log's flight is found: processing the log again (a new version of it, or to read more from it) leaves the flight's session as it is. Imported logs have no pilot from a controller and are never grouped by themselves; neither is anything at startup, after processing or after a pilot change. A flight without a pilot never joins a session by itself, because the remote controller is not a reliable stand-in; by hand it may (user's decision, 2026-10-19), so imported flights can be grouped first and given their pilot later.
- **Suggested sessions group the flights without a session for review** (user's decisions, 2026-10-19). Flights join a suggestion when they take off less than the session gap after its last landing, and are in its group. Pilots don't keep flights apart (user's change, 2026-10-19: a session may have several pilots, and filtering on a group's drones leaves out others flying at the same time); automatic grouping of uploads stays per pilot. Flights without a group are a group of their own (user's correction, 2026-10-19: they're often another group's flights still to be sorted out, which were mixed into a group's suggestions when they fitted any). Suggestions are worked out anew each time and nothing about them is stored, so one that is skipped comes back until its flights are in a session. They are a view of Flights with "Without session": one row per suggestion, with "New session" for one that needs no look. A row opens the suggestion's page (user's decision, 2026-10-19), which looks like the session it would become: its tracks on a map, its facts and its flights, with previous and next suggestion. Each flight's row has its own button to leave it out (user's request: not by selecting rows first); the row stays in place, marked "Left out", and its button puts it back (user's choice after a Carbon review, 2026-10-19): Carbon's inline row actions, Remove and Add, as icon-only buttons in their circled forms (`subtract--alt`, `add--alt`; the user found the bare minus unreadable, and a cross or trash can would read as deleting the flight), with the flight in their accessible names. Left-out flights aren't on the map (user's choice). Pointing at a flight in the table brings out its track on the map, also on a session's page (user's request). A flight left out forms a suggestion of its own once the session is made. The pilot can be set on the suggestion page already, for the flights in the session or one flight (user's request, 2026-10-19): the pilot belongs to the flights, so nothing waits for the session. "Create session" makes it and moves on, to the flights left out or else the next suggestion, which says "Session created" with a link to it until the next step; a separate "Create and edit" was dropped, as there was nothing left to edit. A toast with a link was turned down: easily missed, or it has to be closed. The page's address holds the list's filters and any flight of the suggestion, so it survives suggestions changing. Making all suggestions into sessions at once waits until it turns out to be needed. How (my choices): suggestions are newest first and paged by suggestion, so one is never split over two pages; on phones a row shows only its time and the action.
- **Different pilots are never grouped automatically.** Several pilots in one session is rare, so it only happens when a user merges sessions. A session therefore stores no pilot: its pilots, times and totals come from its flights.
- **Merging** puts all flights in the earliest of the sessions and deletes the others. **Splitting** moves selected flights of a session into a new session. Moving flights to another session is splitting them off and merging.
- **Forming sessions by hand** (user's decision, 2026-10-19), from the flights list: "Without session" shows the flights still to be grouped; selected flights become a **new session**, or are **added to a session** chosen from those within 12 hours of them. Either way they leave the sessions they were in. Flights can also be **removed from their session** (from the list or the session's page); they stay flights without a session, and a session left without flights ends, unless it has comments (see "Comments" below). Suggestions (proposed groupings to accept or adjust) come next.
- **Changing a flight's pilot or group keeps it in its session** (a session may have several pilots and groups).
- **Comments record what happened in a session** (user's decisions, 2026-10-25): they're for keeping a record, not a platform for discussion. A session has a list of comments, each with its author and time, oldest first.
  - **Writing them needs `sessions.edit`** on the session, so Editors and Admins; Viewer stays read only. Whoever sees a session sees its comments.
  - **Authors edit and delete only their own comments**, and an edited comment is marked "Edited". Earlier versions are for the audit log.
  - **Comments are part of the session everywhere** it appears: on its page, in MCP's `get_session`, and later in reports.
  - **A session without flights is an exception.** Without comments it is deleted when its last flight leaves, as before; with comments, its last flight can't leave (removing, adding to another session or splitting it off is refused) and the session has to be deleted explicitly, which deletes its comments. Deleting a session leaves its flights without a session. This may be revised later (user).
  - **Merging moves the comments** to the session that remains. Splitting leaves them on the original session.
  - **The database refuses to delete a session that still has comments** (no cascade), so code that deletes a session has to deal with them first, and none get lost by mistake. A user who wrote comments can be archived, not deleted.
  - How (my choices): deleting a session needs `sessions.edit` on it and is offered on every session, with a confirmation that says how many comments go with it; someone who loses `sessions.edit` can't edit their comments any more, which stay; plain text, at most 4,000 characters, not empty.
- **The session cards show a week or a month, with all their tracks on a map** (user's decisions, 2026-10-21). Hovering a card used to fetch that session's full tracks (hundreds of KB) and was slow; instead the session list, asked with `tracks=1`, includes every flight's track simplified to about 5 m (geo's Douglas–Peucker, six decimals): a month of about 60 flights is around 120 KB in one request. A period also bounds how much the map shows; the cards ask for up to 100 sessions, the backend's largest page, and say when there are more. The table keeps paging through everything. The MCP tools never ask for the tracks.
- **A day strip on each session card** (user's request, 2026-10-21) shows when the flying happened at a glance: 00:00 to 24:00 with a mark per flight and night shaded. Every strip has the same 24-hour scale, so cards compare; a flight past midnight wraps around to the left (user's decision; a second strip is the alternative if that confuses). Night is sunset to sunrise at the first flight's takeoff point, worked out in the browser (SunCalc's formulas, `web/src/lib/sun.ts`). For it the session list returns each visible flight's takeoff, landing, air time and takeoff point (user's approval, 2026-10-21); users already see these on the map. The MCP tools leave them out: apps get no locations.
- **Report fields such as an organisation's "time on" and "time off"** are organisation-specific and are not derived from the flights; they come with session reports.
- **Selecting a pilot on the remote controller** sets who is flying from that moment on.

## Areas

User's decisions, 2026-10-21, unless marked as mine.

- **Areas are named pieces of land** that flights are reported by. They belong to the organisation, not to a group: an area is the same land whichever group flies over it, so every group's flights count towards it. Admins manage them.
- **No switch:** areas appear in the web app once an admin adds the first one. Without areas, nothing about them is shown.
- **Areas are drawn by hand** on the map, one polygon each, without importing files. Drawing snaps to the corners and edges of other areas, never to the area being drawn, so neighbouring areas can follow the same border.
- **Areas don't overlap.** On saving, an area is clipped where it overlaps others; only the area being saved changes, never its neighbours. An area that would be left empty can't be saved (my choice), and the map shows the clipped result. When clipping splits a drawing, each piece becomes an area of its own with the same name, to edit, rename and delete separately; names don't have to be unique.
- **A flight's areas come from its track**, not from what the pilot reports. The takeoff area counts because the track starts at lift-off. Each area's share is the share of the track's points inside it; the flight's air time and distance are divided by those shares so that the parts add up to the flight's totals (my choice). Flight and session pages show one "Area" or "Areas" fact with the air time in each area (user's choice, 2026-10-25, replacing shares of the air time), in minutes, so a corner clipped for a few seconds shows as "<1 min"; areas with the same name count as one. A session's table of flights gets an Areas column when one of its flights crossed an area.
- **MCP gives seconds per area**, which add up across flights and sessions, unlike percentages.
- **Changing or deleting an area recomputes every flight**, archived flights included. There is no archiving of areas: past figures always follow the current areas.
- **The Areas page:** a list of the areas beside a map of them. Clicking an area selects it, clicking outside deselects it. The drawing tools are in a Mapbox-style toolbar under the zoom buttons: New area, Edit shape and Delete; the list's header also has New area, which becomes Cancel while drawing. A new area is named on the map, then appears in the list. Each row's menu has Edit shape, Rename and Delete. No instructions on the page.
- **On flight and session maps**, areas are thin, solid, neutral outlines with their names, so the tracks stand out.
- **How it's built** (my choices): boundaries are GeoJSON in `jsonb`, clipped and tested in Rust with the `geo` crate, without PostGIS. A flight's figures per area are stored in `flight_areas`: computed when the flight is processed, and for all flights in the same transaction that saves or deletes an area (a lock on `areas` keeps the two from crossing). A stretch of track between two points counts half for the area of each. Lists and MCP filter on areas flown: a flight passes with any time in one of the chosen areas, a session with such a flight. MCP totals can be grouped per area. The map uses Terra Draw; snapping to other areas within 12px is our own function (12px the user's choice), and Terra Draw's own pointer distance is 8px. Phones show the areas but don't edit them.

## Batteries

- **Batteries are equipment, read from the logs** (user's decisions, 2026-10-22): registered from the battery serial in each log, like drones and controllers, and listed in Equipment. They have a name and no group (for now). No warning thresholds: the pages show what the logs say and leave the judgement to people.
- **What a flight's log says about its battery is stored per flight** (`flight_batteries`, schema approved by the user, 2026-10-22): charge at takeoff and landing, full and design capacity, cycles, lowest and highest temperature, lowest cell voltage and the largest difference between cells. A battery's state now is that of its latest flight, so nothing is kept on the battery itself. Remaining capacity, highest current and lowest pack voltage are left out (user's decision) until a feature needs them.
- **A flight can have several batteries**, one per slot (user's correction: drones with several batteries exist, the Mavic 3 Enterprise isn't one of them). Logs name one battery serial, so it goes in slot 0; where a log of a drone with more batteries keeps the others' serials is still unknown.
- **The battery records come from the parser's battery group** (static, dynamic and cell voltages); see `backend/vendor/README.md` for what had to be fixed in version 14 logs. Adding the table reprocesses every log once, with the stored DJI keys.
- Who sees a battery, and its figures over all its flights, is under "Equipment" in "Groups and roles". How (my choice): renaming a battery is for admins (`batteries.rename` on the organisation), since it has no group to decide which members may.

## Backend structure

- **One crate, organised by feature** (`flights/`, `sessions/`, `ingest/`, and so on). Each feature has `routes.rs` (HTTP), `service.rs` (policy checks, logic, audit) and `db.rs` (sqlx queries). Cross-cutting concerns (`auth/`, `policy/`, `audit/`) are top-level modules.
- **sqlx** with plain SQL migrations and compile-time checked queries.
- **dji-log-parser is vendored** in `backend/vendor/` with our patches, each explained in `backend/vendor/README.md`. Patches only fix bugs; code we don't use stays as it is. FleetRanger uses the parser to build the DJI key request, but sends it itself so it can store exactly what was sent.
- **Background work** (DJI keychain requests, parsing, re-processing) runs as a loop in the same binary. There is no separate queue: each raw log has a processing status (pending, done, failed) with attempts and the last error. The loop picks up pending logs, and re-processing means setting logs back to pending. CPU-heavy parsing has a concurrency limit. Requests to DJI's keychain API are rate-limited to one per second, start to start (user's decision, 2026-10-19), so the work in between counts towards the wait.
- **Processing progress is shown to admins** in the web app's header. What the loop is doing right now (the log, its step, a pause and why) is kept in memory, since the loop and the API share a process; counts come from the database. A batch is what the loop has processed since it last found nothing pending; once nothing is pending, the status gives the last batch's result (in memory too, so until a restart). It is pushed to the browser over server-sent events (`GET /api/events`, user's request, 2026-10-19). How (my choices): one stream per open app; whatever changes it (the processing loop, an upload) raises a shared signal, and each stream then sends its user the states that differ from what it sent before, at most every quarter second. A refresh every 30 s catches what nothing signals (a command-line import). The response tells nginx not to buffer (`X-Accel-Buffering: no`), and the streams end when the server shuts down, which would otherwise wait for them.

## Web and API

- nginx routes `/api/*` and `/auth/*` to the backend and everything else to SvelteKit.
- The backend owns login and the session cookie (`HttpOnly`, `Secure`, `SameSite=Lax`). SvelteKit holds no secrets and has no database access. During server-side rendering and in form actions it calls the backend over the internal network, forwarding the browser's cookie and client IP.
- The backend trusts forwarded client IP headers only from the internal network.
- **Maps use Mapbox GL JS**, with Mapbox's satellite-with-streets style by default. Each install has its own public access token (`MAPBOX_ACCESS_TOKEN` on the web app), read at runtime so one image serves every install. The browser loads tiles, styles and fonts from Mapbox, which learns roughly which area is viewed; tracks themselves are drawn in the browser and never sent to Mapbox.
- **Charts use Carbon Charts** (`@carbon/charts-svelte`, user's decision, 2026-10-22), Carbon's own chart components, although a line chart adds about 140 KB compressed to the page that shows it.
- **Responses are compressed:** the web app serves its scripts and styles precompressed (adapter-node, Brotli or gzip), nginx gzips HTML (Ubuntu's default) and, since v0.5.0, JSON (the API's and the web app's page data), set in the Ansible repo. Event streams aren't compressed.
- **Sessions are the start page** (user's decision, 2026-10-19): users think in sessions, not single flights. The logbook of all flights is at /flights, named "Flights" in the navigation, for batch work (pilot, group) and filtering by equipment. The sessions list opens as cards beside a map that previews one session at a time (not all sessions at once, to keep it light), and keeps a table view for now (user's decisions). It has the same filters as Flights (user's request, 2026-10-19): a session is listed when one of its visible flights passes them, and still counts all its visible flights (my choice); the filters' options come from flights in a session. The group filter is the exception: it goes by the session's own group (see "Sessions" in "Groups and roles"), and shows only to someone who can read more than one group's flights, in both lists (user's decision, 2026-10-23). Both lists also filter by pilot (user's request, 2026-10-19), with "Unknown pilot" for flights without one.
- **Views:** the same data can be shown in different views, depending on what the user wants to do with it. Sessions, for example, are a table, or cards beside one map that shows the selected session. The view is part of the URL.
- **Times are shown in the organisation's time zone**, one setting per install (`TIME_ZONE`, a zone name such as `Europe/Amsterdam`). Everyone sees the same times, as in reports, and server and browser render the same text. Each time uses the offset of its own moment, so summer flights stay in summer time after the clocks change. All flights are assumed to be in that one zone (user's decision, 2026-10-21), so times carry no zone label: a label worked out for today ("CET") was wrong for half the year's flights. A zone per flight from its takeoff point is possible (time-zone boundary data) if flights across zones become a need.

## Clients

- **Backend:** Rust with axum.
- **Web:** SvelteKit with server-side rendering (Node), TypeScript, pnpm, Prettier and ESLint. The UI follows the Carbon Design System through our own components; see [design-system.md](design-system.md).
- **Remote controller app:** Kotlin, for DJI Enterprise controllers running DJI Pilot 2. The controller is configured to launch FleetRanger on boot. After a pilot is selected, the app starts DJI Pilot 2. The pilot's tile says "Open DJI Pilot 2". The last pilot is on it already, so the same pilot again takes one tap (two with a group to choose; tiles name only the pilot or the group, except a pilot's tile with their one group, user's decisions, 2026-10-23); another pilot or group is chosen through "Other pilot", the list and the group step (see "Flights and pilots" in "Groups and roles"), which goes back to the first screen with them on the tile, so it takes a tap more, on purpose (user's decision, 2026-10-20), as does the very first choice on a controller. A pilot chosen in the list counts at once and is the last pilot from then on, also when DJI Pilot 2 isn't opened through the tile (user's request, 2026-10-20). The app downloads the users it can offer and keeps the list for offline use; it doesn't create users. A pilot who isn't in the list chooses "Not in the list": the flight has no pilot, goes to the queue, and gets its pilot later in the logbook. Finished logs sync over the connections chosen in the app (see pairing and networks below).
- **Pairing links a controller to the install,** for whoever holds `controllers.pair`. The app is downloaded on the controller from the install's public download page, and the backend writes the install's address (`FLEETRANGER_PUBLIC_URL`) into the APK as it serves it: as an ID-value pair in the APK Signing Block, which Android's verifier ignores, so one signed APK serves every install. The app reads it from its own APK on first start. Without it (an APK installed some other way), the pairing screen asks for the address too, which the download page also shows; the app keeps a typed address only if FleetRanger answers there. (A `fleetranger://setup?server=…` link also sets it; the page doesn't use it.) The download page (`/download`, public, linked from the login page) serves one APK file that the install's administrator puts on the server (`FLEETRANGER_ANDROID_APK`, through Ansible); a new app version is a new file. Without the file the page says the app isn't available. The controller's browser can't be recognised (Firefox's user agent names neither DJI nor the model), so nothing depends on detecting it. The pilot then types a pairing code into the app, which pairs at once (user's decisions, 2026-10-23, replacing approval of a code the controller showed, which needed someone logged in nearby and told every user about every waiting controller): nobody logs in on the controller, which is shared, nor in the field. The code is typed one box per character with a dash between the halves, as the web app shows it (user's request); it is one text field drawn as boxes, so pasting and backspace work as usual, and fixing a character in the middle means backspacing to it (tapping a box to change it was left out to keep it simple). The keyboard's Done only closes the keyboard, as Android intends, and Pair is the button (user's decision). The controller then gets a long random token, which it generates itself and of which the server stores only the hash. The token only allows downloading the pilot list and uploading logs.
- **A pairing code is created in the web app** (`/pair`, "Pair a controller"), valid for the time they choose (1 hour to 7 days; 24 hours by default, my choice), and pairs one controller. It is 8 characters without look-alikes (no 0/O, 1/I), stored as text so the creator can see it again: a hash of so short a code would be reversed in seconds. Creators see and revoke their open codes, and those with `controllers.manage` a group's codes; revoking is confirmed first (user's request), though a new code is quick to make. A used, revoked or expired code's row is deleted; who paired a controller is for the audit log. Guessing codes is limited in nginx: 10 pairing attempts a minute per address (user's decision, 2026-10-23, without a limit across addresses), answered with 429, which the app shows as "Too many attempts".
- **A paired controller joins the group chosen with the code** (see "Equipment" in "Groups and roles"). The controller says which group it joined, or that it's in the organisation, with a way to unpair straight away if that's wrong. Controllers paired the old way keep their tokens; an older app that isn't paired can't pair any more and doesn't say why, since it only looks for updates while paired, which the user accepted (2026-10-23) as few controllers wait unpaired and the download page has the new app. It offers the people who hold `flights.fly_for` anywhere, each once, those of its own group first.
- **The controller's API is versioned** (user's decisions, 2026-10-23), as the app updates out of step with the server: `/api/controller/v1/…`, while the web app's API ships with the server and has no versions. Within a version only additions are allowed (new endpoints, new fields in answers, new optional fields or headers in requests), and the app ignores fields it doesn't know; anything else is a new version, and an old version goes once no controller reports an app that uses it. Errors are JSON `{"message": …}`, a sentence for the person (a machine-readable `code` can be added when the app needs one); a malformed request is a 400 like any other. Every request carries a user agent with the app's version (`FleetRanger/0.4.0 (4000) …`) for logs and diagnostics; the path decides the format, and the version would only be used to refuse a release known to be broken. Version 1:
  - `POST /pairing` with `{code, serial, token_sha256}` → `{group: {id, name} | null}`; `DELETE /pairing` unpairs the controller itself.
  - `GET /pilots` → `{controller_group, groups: [{id, name}], pilots: [{id, name, groups, other_groups}]}`: a pilot's `groups` are those they're a member of and fly for, `other_groups` the rest where they hold `flights.fly_for`. Without groups in the organisation the lists are empty and there is no group step.
  - `POST /logs/check` with `{sha256: […]}` (at most 1000) → `{missing: […]}`, the logs to upload; `PUT /logs/{file name}` uploads one, with headers `X-SHA256` and, if chosen, `X-Pilot-Id` and `X-Group-Id`: 201 for a new log, 200 for a replaced one or a duplicate (whose pilot and group are ignored), as PUT puts this file at this name and a repeat is harmless.
  - `PUT /status` with `{app_version, last_sync}`: the whole status every time, `last_sync` (the controller's clock; not in the future) left out until the first sync. It can be sent without a sync, at start.
  - `GET /release` → `{version_code, version_name}` (404 when the install offers no app, or doesn't know its version) and `GET /release/FleetRanger.apk`, both public, so an unpaired controller finds its update too.
- **android-v0.3.0 keeps working** (user's decision, 2026-10-23; nothing older is supported): the unversioned endpoints it calls stay as they are, with its pilot list once per group, which it calls teams, until no controller reports it. Its `X-Team-Id` is the group chosen with the pilot (the groups kept their teams' ids, and its pilot list gives each group's id as the team's), checked like a later app's choice (user's decision, 2026-10-24, after v0.7.0 and v0.8.0 had ignored it and sent its uploads to the queue). `GET /api/download` keeps its `version_code` and `version_name` for its update check.
- **The controller has a settings screen**, which anyone holding the controller may use: which connections logs upload over and the approved Wi-Fi networks, from which date logs sync (all logs, or from a chosen date), and unpairing.
- **Which logs to upload is chosen on purpose** (user's decision, 2026-10-20): after pairing and allowing access to the logs, onboarding asks "All logs" or "From a date", as the settings do, with the date set to today and chosen to begin with (user's decision: no separate "From today", which also keeps the screen within the controller's height), each with the number of logs on the controller it covers (user's request). Until someone continues, the controller uploads only today's logs. How (my choices): the question comes again after every pairing, and controllers paired before this step keep their setting.
- **Unpairing** is done on the controller itself or with `controllers.manage` on its group. The token stops working immediately.
- **Logs upload over the connections chosen on the controller:** unmetered Wi-Fi networks (the default), approved Wi-Fi networks only, or any connection, mobile data included. Android doesn't recognise every hotspot as metered (iPhones' and 4G routers' often not), so the app says so and points to approved networks for certainty. For approved networks the app sees the network's name (on Android this needs the location permission, which DJI Pilot 2 needs anyway); the settings approve the current network, and approved networks can be removed again. Over Wi-Fi it never uploads over a network Android reports as metered, such as most phone hotspots; only "any connection" uses metered networks.
- **The controller asks before uploading which logs the server lacks** (user's decision, 2026-10-19), so a log already stored isn't sent again, also after moving to another server. It sends the SHA-256 of the logs it would upload, up to 1000 per request (`POST /api/controller/v1/logs/check`), and uploads only those the server names; the check after an upload stays. How (my choices): the app remembers which logs the server has (by name, size and modification time), so it only asks about new or changed ones, and it forgets that record whenever it pairs, after which it asks about every log once. A server that can't answer (an older version) gets every log, as before.
- **The controller app's UI is Jetpack Compose with our own Carbon theme:** Carbon's tokens (the same colours, IBM Plex and spacing as the web app) in a small set of our own components, as on the web. Carbon has no official Android library, and a community one would be a third-party dependency for a handful of screens.
- **The app updates itself from its install, with a person confirming.** Next to the APK the server keeps the release's build metadata (`FleetRanger.json`), so the controller's `GET /release` reports its version. The app checks whenever it comes to the front (user's request, 2026-10-20: a daily check alone showed a release up to a day late), once a day from the upload service, and on request (Settings › App); a newer release shows a hint on the main screen. Updating downloads the release and opens it in Android's installer, the same screens as installing from the download page: the person holding the controller confirms (the first time also allows FleetRanger to install apps), and "App installed" offers to open the new version, which Android 10 wouldn't let the app do itself. Silent updates would need the controller to be a managed device.
- **Only tagged commits become app releases** (`android-vX.Y.Z`); the version name is the tag's version and the version code is derived from it, so it grows with every release. `android/release.sh` refuses anything else. Releases are signed with one release key, kept in the password manager and never in the repository; R8 shrinks them.
- **The APK is built with Gradle in a pinned Docker image for the machine's own architecture** (user's decision, 2026-10-20, replacing an x86_64 image that ran wholly under QEMU on arm64 and took 12 to 15 minutes per release). Gradle, Kotlin and R8 are Java and run natively; only aapt2, which Google publishes for x86_64 Linux alone, runs under QEMU on arm64, with x86_64 glibc copied from the x86_64 variant of the same pinned base image. A clean release build takes under a minute.

- **MCP server** (user's decisions, 2026-10-20): AI assistants can query an install through the Model Context Protocol, as the user they act for, with the user's own access, read only (user's decision, 2026-10-23, replacing "everyone counts as a member"): an admin's assistant sees what the admin sees. `directory` says who the user is and which groups they fly for as a member, so "my flights" and "my group" can be answered. Read-only, summaries only (no raw logs, telemetry or tracks), and off by default: an install switches it on, since answers go to the assistant's provider. Its tools (proposed and accepted 2026-10-20): `directory` (the groups, pilots, drones, controllers and areas of the flights the user sees, with the time zone and today), `flight_totals` (flights, sessions, air time and distance for a period and filters, grouped by nothing, group, pilot, drone, controller, day, week, month or area; per pilot over a period is the common question), `list_sessions` (with each session's own group, which its groups filter applies to, as in the web app), `get_session`, `list_flights` (also without pilot or without session), `get_flight` (without its track) and `list_equipment` (with controllers' sync status). No locations until areas can be assigned (user's decision); no suggested sessions, which belong with writes. Built with the official Rust SDK (`rmcp`) at `/mcp` in the backend, switched on with `FLEETRANGER_MCP=on` (user's decisions, 2026-10-20). Assistants in claude.ai connect from the provider's servers, so they need a public HTTPS address and OAuth, with FleetRanger issuing the tokens (see "Identity and access"). Release builds accept only those access tokens on `/mcp`; debug builds also accept a login session (cookie, or its token as a bearer token), for testing with a local assistant such as Claude Code.

- **The site counts visitors with Plausible** (user's decision, 2026-10-19): plausible.io's cookieless script, so the site needs no cookie banner. The app has no analytics.
- **The site speaks to DJI Enterprise operators with strict data privacy requirements** (user's decisions, 2026-10-19): FleetRanger gives them a logging platform on their own premises. It names no customers, the contact is info@mapture.ai, and it claims support for DJI Enterprise only. A hosted offering comes later and isn't on the site until it exists.

## Apps

- **Organisation-specific features are separate applications** (user's direction, 2026-10-25): an item in FleetRanger's navigation opens the app in a new tab, and the app talks to FleetRanger's public API (see "Public API"). Its code lives outside this repository. Each app has its own subdomain (user's decision, 2026-10-25), not a path under FleetRanger's address: the browser then keeps it apart from FleetRanger (its `__Host-` cookie and the backend's origin check), so an app can do only what its token allows. WebAssembly plugins loaded by the backend were discussed and parked, as feasible too.
- **Admins add trusted apps on an admin page** (user's decision, 2026-10-25), replacing the earlier decision to declare them in the install's configuration: self-hosting organisations shouldn't have to edit files on the server, and admins can already impersonate users, so trusting an app gives them nothing new. An admin types in the app's name, address and fixed return addresses; an app added this way skips the consent screen (user's direction) but still sees only what its user may see, and removing it ends its users' tokens. Apps that register themselves, such as assistants, keep the consent screen (my recommendation). Apps describing themselves in an OAuth Client ID Metadata Document, so the admin only pastes an address, can follow later (user, 2026-10-25: not worth the work yet).
- **Apps appear only in the navigation** (user's decision, 2026-10-25): an item that opens the app; no actions inside FleetRanger's pages, such as on a session, until people miss them.
- **Apps declare their own permissions and roles** (user's decision, 2026-10-25; where, now that apps are added on an admin page, is open), as Entra ID's app roles do. Admins give them per person on a group or on the organisation, like the built-in roles and in the same dialogs, under the app's name. FleetRanger manages who holds them; the app decides what they mean and asks the API for the user's permissions per group. So an app's users need no access to sessions. Roles that admins compose from permissions, the apps' included, may follow later (user's direction).

## Public API

User's decisions, 2026-10-25, unless marked as mine. Built in `backend/src/api_v1`; its reference is generated from the code at `/api/v1/openapi.json`, with the conventions in `backend/src/api_v1/description.md`.

- **Separate from the web app's API:** `/api/v1/…` is a small set designed for apps, next to `/api/…`, which keeps changing with the web app's pages. Both use the same services and access rules. Within a version only additions are allowed, as for the controller's API. While FleetRanger is at 0.x and no app depends on it, v1 can still change.
- **Off unless switched on** (`FLEETRANGER_API=on`), like MCP; OAuth runs when either is on. The organisation's name for apps is `FLEETRANGER_ORGANISATION_NAME` for now.
- **Ready for several organisations:** no organisation in the paths, settings come from the organisation rather than the install, and things are identified only by ids, never by serials or email addresses.
- **Apps act for a user through OAuth**, under that user's access, with tokens for the resource `/api/v1`; a token for `/mcp` doesn't work there, nor the other way round (401). An app names the resource it wants a token for (RFC 8707): FleetRanger never guesses it, also with only one switched on. Service accounts, for apps acting without a user, come later as an addition.
- **Scopes are per resource and level:** `<resource>:list`, `:read` and `:write`, each level including the ones below it (my proposal). v1 issues `sessions:list`, `sessions:read` (comments), `flights:list`, `groups:list`, `areas:list` and `equipment:list` (drones, controllers and batteries together, as `equipment.read` covers them; separate scopes can follow with `equipment:list` including them). A scope says which resources an app reaches and how deep; the user's permissions still decide each item. For now the API maps scopes onto today's permissions; once the API has settled, the permissions are brought in line with the scopes, including a summary level for people, to see sessions and flights without their details.
- **Read-only and without locations** for now: no tracks, area boundaries or takeoff points. Tracks can come later as an expansion behind `flights:read` and a details permission. Writes, events and syncing another system are additions for when an app needs them.
- **Answers have a fixed base shape**, whatever the user's permissions: references are ids, and `expand` (Stripe's method) puts the object in the same field, or adds a session's `comments` and `flights`, which aren't in its base shape. Paths nest with a dot, at most three levels (my choice). What the web app shows on a session or flight (its group, pilots, areas and equipment, and comments' authors) comes with it, so expanding it needs no further scope; whatever reaches another resource or level does (`comments`: `sessions:read`; a session's `flights`: `flights:list`; a flight's `session`: `sessions:list`). A missing scope is a 403, never left out silently; anything the user can't see is a 404.
- **People's names come with what they appear on:** whoever sees a session or flight sees its pilots' names and its comments' authors. There is no list of pilots or users.
- **Lists are paged with a cursor** (keyset), `limit` and `cursor` in, `items` and `next_cursor` out, without counts or page numbers; every list is paged, each in one fixed order whose keys don't change (my proposal), so a pass through all pages misses nothing. Filters repeat for several values (or within a filter, and between filters), with `none` for "without one"; days are the organisation's. A session's figures count the flights the user sees, and filters decide only which sessions are listed.
- **Field names:** a session has `first_takeoff_at`, `last_landed_at` and `flight_count` (no comment count); per-area figures are `areas: [{area, air_time_s, distance_m}]`. `/me` is only `id` and `name` until permissions match the scopes.
- **The reference** is generated with `utoipa` and `utoipa-axum` from v1's own response types; no Swagger UI on installs. Fields that can be null are optional in it, not required, which leaves room to omit them later.

## Customer-specific needs

FleetRanger stays generic. Needs specific to one organisation are left out until they are actually built, and are then implemented in the simplest form. They are generalised only when a second organisation needs them. No customer data goes in this repository: no real logs, locations or names. Tests use synthetic or anonymised logs.

**Flexibility stays out of sight until it's needed** (user's decision, 2026-10-25). Integrations, apps and support for different kinds of organisations must not make FleetRanger harder for those who don't use them: sane defaults work in the background, and choices appear only once an organisation needs them. For example, an install without apps shows no app items or app roles, one without groups never asks for a group, and with one organisation there's no organisation to choose.
